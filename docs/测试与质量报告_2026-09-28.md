## 五、缺陷清单（按优先级）

### P0（核心功能损坏，必须修复）

**P0-1｜CrossRef 引用排序摧毁相关性 → 引擎①②④大面积降质**
- 现象：`paper_search("retrieval augmented generation")`（默认 `sort="cited"`）返回 DFT 物理论文；`topic_radar` 高引代表作是 ImageNet/Akaike
- 根因：CrossRef 的 `sort=is-referenced-by-count` **完全忽略查询相关性**（已用原始 API 复现：`query` 与 `query.bibliographic` 均如此）。[academic.py:159](../src/mcp_server/tools/academic.py) 默认 `sort="cited"`，[crossref_tools.py:145](../src/mcp_server/tools/crossref_tools.py) 直接把该排序传给 CrossRef
- 修复：CrossRef 侧**永远用 relevance 排序**取 `rows×3`，客户端按被引重排 + **相关性守卫**（查询词与标题的 token 重叠率 < 阈值即丢弃或打 `low_relevance` 标）

**P0-2｜author_profile 100% 失败 + 4xx 污染熔断器**
- 现象：任何学者都"未找到"（Jason Wei 在 OpenAlex 真实存在，h=20）
- 根因：[openalex_tools.py:223](../src/mcp_server/tools/openalex_tools.py) 的 `select` 含非法字段 `coauthors`（OpenAlex 返回 400 "not a valid select field"，已复现）→ `fetch_json` 返回 None → 误报"未找到"；且 [unified.py:203](../src/mcp_server/tools/unified.py) 把 4xx 也计入熔断 → 3 次即把 OpenAlex 熔断 60s → **拖垮 paper_search/topic_radar 的最优数据源**（测试中真实发生了连锁反应）
- 修复：① 删除 `coauthors`（如需合作网络走 works.authorships）；② 熔断只计 429/5xx/网络错误，4xx 属代码缺陷应记日志告警而非熔断；③ 区分"源不可用"与"确实不存在"两种 message

**P0-3｜cross_search 主源（S2）长期 429 + 降级路径返回噪声 + 可行性评分失真**
- 现象：attention × protein 返回 Lowry 1951、公司理论 1976，却给出 8/10「🟢低风险」
- 根因：S2 未配 API key，公共池限流（复现 429）；降级到 `paper_search(f"{a} {b}")` 叠加 P0-1；[academic.py:506](../src/mcp_server/tools/academic.py) 的 `_assess_cross_feasibility` 用噪声计数算分
- 修复：① `.env.example` 提示申请 S2 free key；② 降级结果必须过 P0-1 的相关性守卫，守卫后为空就如实返回"无交叉工作"；③ 交叉计数为 0 时可行性评分应输出"数据不足"而非高分

**P0-4｜paper_distill 按标题检索确定性返回错论文**
- 现象：CoT 论文全名 → 返回 Sanger 1977 / lme4 2015（两次复现，两次都错）
- 根因：[academic.py:356](../src/mcp_server/tools/academic.py) 标题路径 `paper_search(identifier, rows=1)` 只取第 1 条，而 cited 排序把高引错论文顶到第一
- 修复：标题精读改用 S2 `/paper/search/match`（专为标题匹配设计）或 top-5 + 标题 token 相似度打分选优，低于阈值返回候选列表让用户确认

**P0-5｜主 Agent 回答的 Markdown 结构性坍塌（Wave 0 起即存在，用户感知最强）**
- 现象（实测持久层证据）：今日 4 个成功用例的**最终保存消息全部 `newlines=0`**，但含 `##` 字面量——标题、表格、列表、分段在用户气泡中坍塌为一整行，markdown 无法渲染（本地会话存储 `data/local_sessions/messages/` 可复现）
- 根因：[chat.py:932](../src/api_view/api/chat.py) 对**每个流式 token 单独**调用 `strip_leaked_tool_meta`，该函数末尾 `.rstrip()` 把「恰好是换行符的 token」清空后 `continue` 丢弃。DeepSeek 主模型流式 token 平均 1 字符 → **每个换行都单独成 token → 100% 被吞**。子 agent 路径（大块文本）仅尾部换行受损，故 E3 用例保留了 101 个换行（对照实证）。该函数设计意图是清洗整段泄漏 JSON，被误用于逐 token 通道
- 连锁：`done.content`（前端权威替换文本）与持久化 display 消息同源同损；`normalize_markdown` 只修标题前缀/表格折叠，无法凭空恢复换行；前端 `breaks:true` 无换行可用
- 修复（一处小改，收益极大）：**删除 line 932 的逐 token 清洗**（泄漏清洗已在 finalize 的 `normalize_assistant_markdown` 兜底），同时在 `done` 事件发送前对 `collected_content` 套同一清洗（顺带修掉 P1-1 的记忆 JSON 泄漏）

### P1（应尽快修）

**P1-1｜memory_update 偏好 JSON 泄漏到用户气泡**
- 现象：E1 回答尾部出现 `{"research_direction": "large language model agents", ...}`
- 根因：`done` 事件的 `collected_content` 从未过 `strip_leaked_tool_meta`（[chat.py:626](../src/api_view/api/chat.py) 只清洗 display_messages；[chat.py:1061](../src/api_view/api/chat.py) 原样下发）。前端 `data.content || fullContent` 直接替换气泡 → 用户实时看到泄漏（刷新后历史才是干净的）
- 修复：发送 `done` 前对 `collected_content` 套同一清洗（与 P0-5 的修复合并处理；更彻底的方案是 memory JSON 走结构化通道而非模型文本尾巴）

**P1-2｜DeepSeek 402 原样透传给用户**
- 现象：前端会看到英文 `Error code: 402 - Insufficient Balance`
- 修复：错误映射表（402→"模型服务余额不足，请充值"、429→"请求过于频繁"、5xx→"模型服务暂不可用"）；有条件时 402 自动降级 summary model 并提示

**P1-3｜smoke 测试断言无效**
- `smoke_academic.py` 只断言 `count>0`——返回垃圾也算 PASS，本轮 P0-1/P0-2 因此长期漏网
- 修复：加已知答案断言（如 RAG 检索 top5 必须命中 Lewis 2020 或 DPR；精读 CoT 返回的年份必须 ≥2022；author_profile("Yoshua Bengio") 必须 ok）
